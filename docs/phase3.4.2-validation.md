# Phase 3.4.2: package consistency and operation ownership

## Reproduced defect

The released 3.4.1 ordinary update included `app/integrity-manifest.json`, but its protected Setup package did not. A protected upgrade could therefore retain a previous release's manifest while installing a newer UI. The regression test downloaded both original release ZIPs, checked their published digests, and reproduced the omission. Neither the original assets nor local user baselines were removed to make this test pass.

## Changes

- Both delivery paths now share the same final UI, including Change Target and protected-update routing.
- A shared manifest writer runs after each delivery path finishes building its files. The ordinary update covers four delivered app components; Setup covers six. The operation library is also delivered with the protected workers. These counts do not imply that every installed protected component is covered by Guardian's app manifest.
- Guardian rejects missing coverage, duplicate entries, unexpected paths and wrong-version metadata. Integrity remains on demand; startup does not run it automatically.
- Baseline writes flush a new file before replacement and retain one previous baseline. Damaged/unreadable records remain visible as problems rather than being silently accepted as a new baseline.
- One shared operation implementation serializes ownership changes. Live operations are not evicted based on marker age. Process start time distinguishes a reused PID. Uncertain ownership fails closed. A proven-dead owner can be replaced while recording the last recovery locally.
- A rejected repair contender no longer publishes over the active worker's state. The UI preserves the preceding result until a new worker publishes and gives an explicit message if no new run starts.
- Generated bytecode, test fixtures and runtime state are excluded from source control.

## Native validation evidence

Development run `35445195042` completed successfully with 38 assertions. The tests ran on Windows PowerShell 5.1, WPF and .NET Framework. Evidence and validated development packages are retained as Actions artifacts.

The permanent release workflow reruns 36 assertions on both final delivery packages; the two additional development assertions reproduced the original 3.4.1 omission. Publication cannot run unless the current package/runtime validation job succeeds. It also retains the repository-isolation, privacy scans, exact-artifact, digest and release-asset checks.

Verified scenarios:

- Final UI parity and feature markers in both delivery paths.
- Native WPF button invocation of the actual final packaged Guardian handler.
- Replacing stale metadata through the actual package file list.
- Establishing then confirming a clean baseline.
- Same-size file corruption, invalid manifest coverage/paths/version, damaged baseline and blocked baseline access.
- Preserving the baseline on rejected verification and recovering after the fixture fault is removed.
- Keeping a live legacy owner even with an old marker; preserving unreadable ownership.
- Mutual exclusion between real child processes, recovery after killing a disposable worker, and refusing to remove a replacement owner's marker.

### Scope and limits

Guardian's Windows integration probes are fixture stubs in this suite. WPF event invocation and process/file ownership operations are native, not textual marker checks, but this is not a complete fresh-install/UAC/logon/interactive-desktop acceptance pass. No production service, Tailscale adapter or user's machine is disrupted by these tests.

The coordinator is not a local security boundary. A baseline and its file hashes detect accidental corruption/change; they are not a signed trust root against a malicious local administrator.

Atomic baseline replacement and abandoned-operation handling do not prove whole-update recovery after power loss. Reboot-mid-Setup, full rollback, installer identity across alternate-user UAC and persistent restart acknowledgement remain separate acceptance work. Do not mark the entire crash-recovery phase complete from these tests.

## Field acceptance after publication

On the existing installation: update through the protected Setup path, check integrity twice (established, then confirmed), run the normal check, and verify tray Exit/reopen. A successful field check does not replace the outstanding failure-lab scenarios above.
