## Safety contract retained

Only fixed local service, startup, client and backend observations are policy inputs. No peer availability, address, route, latency, diagnostic result or arbitrary error text can authorize automatic recovery. A decision/reservation is not an action; starting a task is not recovery. Missing or unconfirmed evidence is not Healthy.

Intentional disconnection, sign-in, approval and other-user states require attention. An observed intent/authentication hold survives later service loss until explicit Running evidence releases it. A disabled service is not re-enabled automatically. Missing installation or uncertain installed-path/service registration prevents mutation. Production uses fixed installed paths, not a user-writable PATH fallback, and performs no self-elevation, login/up command, peer probe, adapter reset or broad Windows network reset. Other VPN and network settings remain outside the action set.

Candidate faults need two comparable observations separated by at least 30 seconds for service/client faults or 60 seconds for Starting/NoState. A gap over ten minutes or intervening missing evidence breaks continuity. Reservations use 15-, 30- and 60-minute backoff, with three unresolved attempts before attention is required. Three spaced healthy observations over ten minutes may reset the incident budget; rapid events and preference toggles do not. These timings are conservative product policy, not network guarantees.

The policy store is bounded to 16 KiB and one predecessor. Settings accept only a boolean enabled and optional round-trip UTC updatedUtc. Duplicate/escaped aliases, wrong types and unknown fields are rejected. Invalid, locked, oversized or inconsistent state is preserved, never reset to manufacture permission. The settings writer uses a separate persistent lock and flushed atomic replacement. Migration preserves a legacy last-attempt cooldown without promoting the legacy repaired label to success.

The local collector uses only status --json --peers=false, hidden child processes and bounded concurrent byte reads. Output retention is capped at 64 KiB, including newline-free output. Timed-out, truncated, malformed or failed reads cannot become Running. Raw output and identifiers are not returned or persisted by the collector. Installed path/registration checks are not cryptographic publisher provenance.

The worker acquires the real shared operation lease before observation and retains it through recovery and publication. Existing marker schema and kinds are preserved; a read-only IsCurrent check verifies lease ID, PID and process start. Ownership, opt-in, environment and fresh intent are checked again at each final action boundary. Service stop/start are individually authorized. Cancellation after a completed stop does not override opt-out by blindly dispatching start; the partial action is reported honestly. Schema-3 results contain a reservation stamp and at most three named completed actions with timestamps, fixed vocabulary, counters and run ID. Results are bounded to 8 KiB with one predecessor. Schema-2 reads remain compatible without inventing exact action names. Corrupt or foreign-owner evidence is not overwritten.

These protections are not a local-administrator security boundary, an atomic guarantee against all external user/network changes, signed provenance, or proof of whole-PC power-loss recovery. The new permission tests do not certify user-writable state as a trusted security boundary.

## Background lifecycle contract

Worker-side History distinguishes a reserved attempt, specifically completed local actions, confirmed recovery, unconfirmed completion and a prior attempt with no recorded completion. It uses fixed typed events and the existing five-field schema. Stable per-run/per-slot event IDs prevent duplicate replay. Routine healthy checks do not manufacture activity. UI and background entries share the original 40-record, 32 KiB and 30-day bounds.

Reconciliation is limited to current and previous worker snapshots, not an unlimited outbox. Only a new real maintenance-lease owner may classify a prior nonterminal snapshot as interrupted; a UI read cannot label live work that way. Locked or damaged History cannot change the worker's actual outcome. Readable snapshots still available can be replayed later, but prolonged History unavailability can exceed the bounded replay window. No lossless audit guarantee is made. The UI distinguishes reconciliation failure from an ordinary failed History append.

Resident event episodes settle for 10-30 seconds, coalesce bursts, preserve minimum dispatch spacing across preference toggles, defer for busy operations and expire rather than retry endlessly. One follow-up can confirm a fault. The scheduled entry suppresses a new observation inside thirty seconds of the previous recorded check. This is not a claim that every OS trigger avoids launching a process.

Setup defines an indefinite five-minute fallback, a current-user logon check and delayed system/network event subscriptions. Checks do not wake the PC or require remote reachability. Event follow-ups are bounded. Existing client/service/backend observations in the resident UI remain useful; fully exited sessions do not gain process-exit auditing or a continuously resident monitor. Missed event delivery retains the fallback. History can be written while the UI is exited; banners still require the resident UI and historical recoveries are not replayed on a cold start.

## Work still required before a Phase 6 release

1. **Windows lifecycle coverage.** Real service control, client reopen, the PT5M fallback, service-event triggering and task identity are already exercised on disposable Windows runners. Still exercise actual suspend/resume, logon and network/VPN transitions, unavailable event channels, event storms and foreground/tray/exited behavior. The five-minute fallback remains the correctness backstop when an event is missed.
2. **Authenticated recovery boundaries.** The real unauthenticated installation, sign-in hold, disabled service, eligible service start and exact client reopen paths are covered. Still verify recovery against an authenticated local backend, sustained Starting/NoState stop/start behavior and relevant dependency failures without using a real user's tailnet.
3. **Background and notification edge cases.** Bounded History, cold-start non-replay, opt-in, duplicate suppression and background writes are covered. Still exercise longer store unavailability, additional killed-worker boundaries and physical Windows notification/quiet-mode behavior. No exited-UI banner or lossless unlimited audit guarantee is promised.
4. **Setup and identity acceptance.** Genuine 5.2.1 migration, protected handoff, requester-SID enforcement, restart acknowledgement, protected permissions, persistent payload-file recovery and replay to the final Windows integration state are covered. Approval by a different Windows account is intentionally refused so per-user state cannot migrate into the wrong profile. Physical interactive UAC/desktop behavior and true whole-PC/storage power interruption remain separate acceptance work.
5. **Trust and hostile-local-state limits.** Unexpected files, nested content, reparse/hard-link redirection, wrong root types and cross-user recovery journals are refused in the tested paths. Continue preserving evidence under concurrent hostile replacement/race cases and keep the product model explicit: local administrator access is not treated as a cryptographic security boundary. Publisher signing/provenance remains distinct from package SHA-256 and protected ACL checks.
6. **Publication and final acceptance.** The release workflow now consumes the exact artifacts produced by validation, requires a clean-runner compatibility job before publication, rechecks artifact digests and refuses force-pushing the manifest. A real future `main` publication must still pass those gates with the final release source. Whole-PC power-loss, physical desktop/UAC and the remaining Phase 10 failure-lab work cannot be claimed from development CI alone.
